# EdtWorktree 3.0: переносимая установка и настройка из CLI

Дата: 2026-10-28. Статус: черновик на согласовании.

## 1. Зачем

Модуль `EdtWorktree` сейчас работает на машине автора, но новый пользователь на
другом ПК с Windows упирается в баги конфигурации, зашитые пути и соглашения, а
настроить проекты может только правкой JSON. Цель 3.0: разработчик 1С ставит
модуль одной командой, настраивает его несколькими короткими командами `edt` и
сразу работает с задачами в git worktree, не зная внутреннего устройства.

## 2. Сценарий нового пользователя (утверждён)

1. Установка одной строкой в PowerShell 7:
   ```powershell
   irm https://raw.githubusercontent.com/gidragir/edt-worktree/main/install.ps1 | iex
   ```
2. `edt setup`: указывает три каталога.
   - `repos_root` — где лежат клоны проектов; каждый клон стоит на своей
     эталонной (default) ветке;
   - `worktrees_root` — где создаются git worktree задач;
   - `workspaces_root` — где хранятся рабочие области EDT и эталоны.
   EDT находится автоматически.
3. Регистрирует проект: `edt project add <имя>` (или все незарегистрированные
   клоны сразу) и номерами отмечает рабочие расширения.
4. `edt warmup <проект>`: собирает эталон с индексами и валидацией.
5. `edt open` в каталоге worktree либо `edt open <проект> <ветка>`, и работает.

В репозиториях проектов модуль ничего не создаёт: вся настройка живёт на машине
пользователя.

## 3. Цели, не-цели, анти-цели

**Цели**
- Установка, обновление и удаление — по одной команде; повторный запуск
  установщика безопасен и обновляет модуль.
- Вся настройка (пути, проекты, расширения) доступна из CLI без правки JSON.
- Минимум ключей у команд: `warmup` без ключей, у `open` только `-NoGui` и
  `-Refresh`.
- Исправлены все проблемы аудита переносимости (раздел 9).
- Конфиг пользователя 2.x переносится в 3.0 автоматически.

**Не-цели**
- Публикация в PowerShell Gallery.
- Поддержка Windows PowerShell 5.1, Linux, macOS.
- Конфиг на уровне репозитория проекта (`.edt-worktree.json`).
- Автоматическая установка git, PowerShell 7, EDT или JDK: установщик только
  проверяет и подсказывает команду (`winget install ...`).

**Анти-цели (провал, даже если «работает»)**
- Модуль закрывает чужую IDE или теряет несохранённую работу.
- Модуль трогает рабочие области или клоны при установке, обновлении, удалении.
- Сохранение конфига теряет данные пользователя.
- Чтобы начать работать, пользователь должен читать код или редактировать JSON.

## 4. Установка

### 4.1. Установщик `install.ps1` в корне репозитория

Запускается как `irm <raw-url> | iex` и как обычный файл из клона (режим
разработчика). Под `iex` нет `$PSScriptRoot` и `param()`; параметры передаются
через переменные окружения или формой
`& ([scriptblock]::Create((irm <url>))) -NoSetup`.

Параметры: `-InstallDir` (по умолчанию `%LOCALAPPDATA%\EdtWorktree`),
`-Branch` (по умолчанию `main`), `-NoSetup`.

Шаги:
1. Если запущен не в PowerShell 7+: сообщение с командой
   `winget install Microsoft.PowerShell` и выход без изменений.
2. Проверка git; без git — подсказка `winget install Git.Git` и выход.
3. Если установщик запущен из клона модуля — использовать этот клон. Иначе
   `git clone` в `InstallDir` либо, если клон уже есть, `git pull --ff-only`.
4. Junction `Documents\PowerShell\Modules\EdtWorktree` → клон (фолбэк:
   symlink, затем копия с предупреждением, что `self-update` в копии не работает).
   Путь `Documents` брать через `[Environment]::GetFolderPath('MyDocuments')`
   (учитывает перенаправление в OneDrive).
5. Каталог `bin` клона в PATH пользователя (без дублей) и в PATH текущей сессии.
6. Проверки окружения с итоговой таблицей: найден ли 1C:EDT, найдена ли JDK 17 с
   JavaFX. Это предупреждения, не ошибки.
7. Если сеанс интерактивный и нет `-NoSetup`, а пользовательского конфига ещё
   нет — запустить `edt setup`. Иначе напечатать «следующий шаг: edt setup».

Старый `scripts/install.ps1` удаляется (его логика переходит в `install.ps1`).

### 4.2. Обновление и удаление

- `edt self-update`: `git pull --ff-only` в клоне модуля и перезагрузка модуля.
  Требует git в PATH (без фолбэков на пути Git).
- `edt uninstall`: удаляет junction модуля и запись `bin` из PATH пользователя.
  Конфиг, клоны, worktree и рабочие области не трогает. `-Purge` дополнительно
  удаляет каталог установки и `%APPDATA%\EdtWorktree`. Перед удалением показывает,
  что именно будет удалено, и спрашивает подтверждение (`-Yes` пропускает).
  `scripts/uninstall.ps1` удаляется.

## 5. Конфигурация

### 5.1. Один файл

`%APPDATA%\EdtWorktree\config.json` (переопределяется `EDT_CONFIG_PATH`).
Пишется UTF-8 без BOM. Сохранение всегда пишет схему целиком: ни одна секция
и ни одно известное поле не теряются (раздел 9, п. 3).

```json
{
  "version": 3,
  "paths": {
    "repos_root": "D:\\projects\\default",
    "worktrees_root": "D:\\projects\\worktree",
    "workspaces_root": "D:\\workspaces\\worktree"
  },
  "edt": {
    "cli_path": null,
    "vm_path": null,
    "prefs_source": null,
    "max_heap": null,
    "gui_max_heap": null,
    "extra_vmargs": "",
    "timeout_sec": 7200
  },
  "git": {
    "remote": "origin",
    "branch_prefix": "feature/"
  },
  "projects": {
    "ka-intertop-4edt": {
      "ref_branch": "pre-prod",
      "cf_project": "src/cf",
      "extensions": ["src/cfe", "src/cfe_ad"]
    }
  }
}
```

- `null` означает «определять автоматически при каждом запуске»: `cli_path` —
  самый новый найденный 1C:EDT, `max_heap` и `gui_max_heap` — по свободной
  памяти, `vm_path` — см. 7.3. Абсолютный путь пишется, только если пользователь
  задал его явно.
- Имя проекта — имя папки клона в `repos_root`.
- `ref_branch` запоминается при регистрации из текущей ветки клона; диалог
  `project add` показывает её и даёт поправить (клон мог временно стоять на
  другой ветке).
- `cf_project` и `extensions` — пути относительно корня клона. `extensions` —
  список **рабочих** расширений (allow-list): только они попадают в эталон.
- Ключи `max_heap`, `gui_max_heap`, `extra_vmargs`, `vm_path`, `prefs_source`,
  `git.*` — для тонкой настройки, в основной справке не показываются; меняются
  через `edt config set <ключ> <значение>`.

### 5.2. Миграция с 2.x

При первом чтении конфига без `version: 3`:
- источники: текущий `%APPDATA%\EdtWorktree\config.json` (ключи `paths`, `edt`,
  `defaults`) и `~/.config/1c/projects.json` (ключи `$schema`, `defaults`,
  `worktree`, `projects`); при конфликте побеждает `%APPDATA%`;
- соответствие: `paths.projects_root` → `repos_root`, `worktree_root` →
  `worktrees_root`, `workspaces_root` / `worktree.root_dir` → `workspaces_root`;
  `edt.cli_path` / `defaults.1cedtcli` → `edt.cli_path` (только если файл
  существует, иначе `null`); `defaults.edt_prefs_source` → `edt.prefs_source`;
  JVM-поля → `edt.*`; `projects.<имя>.active_extensions` (имена папок) →
  `extensions` (`src/<имя>`, только существующие); `cf_project` переносится;
  `ref_branch` = прежний `reference_branch` проекта, иначе общий, иначе текущая
  ветка клона;
- исходные файлы сохраняются рядом как `*.v2.bak`, legacy-файл в
  `~/.config/1c` не удаляется (его читают другие инструменты автора);
- результат и что было перенесено печатается одним блоком.

После миграции модуль `~/.config/1c/projects.json` больше не читает.

## 6. Команды CLI 3.0

Ключи принимаются в стиле PowerShell (`-NoGui`) и nushell (`--no-gui`), как
сейчас. Для изменяющих команд остаются `-WhatIf` и `-Yes`.

| Команда | Что делает |
|---|---|
| `edt setup` | Мастер: три каталога (с предложением создать отсутствующие), показ найденного EDT, затем предложение зарегистрировать найденные клоны. Без диалога: `edt setup -ReposRoot ... -WorktreesRoot ... -WorkspacesRoot ...`. Повторный запуск показывает текущие значения как значения по умолчанию. |
| `edt project list` | Таблица: проект, эталонная ветка, текущая ветка клона, рабочие расширения / найденные, есть ли эталон. |
| `edt project add [имя]` | Регистрирует клон из `repos_root`. Без имени — все незарегистрированные клоны по очереди. Находит конфигурацию и расширения (7.1), показывает нумерованный список расширений, пользователь вводит номера (`1 3 4`, диапазоны `2-5`, `все`, `нет`). В неинтерактивном сеансе: `-Extensions all|none|<имена>` обязателен. |
| `edt project ext <проект> [+имя ...] [-имя ...]` | Без аргументов — тот же нумерованный список с текущими отметками. С аргументами — без диалога. Имена — по папке (`cfe_ad`) или относительный путь. |
| `edt project set <проект> -RefBranch <ветка> \| -CfProject <путь>` | Редкие правки. |
| `edt project remove <проект>` | Убирает из конфига; файлы не трогает. |
| `edt warmup <проект>` | Собирает эталон (7.2). Ключей нет. Без имени — проект текущего каталога. |
| `edt open [проект ветка] [-NoGui] [-Refresh]` | Как сейчас, с моделью веток из 7.4. |
| `edt add <расширения>` | Доимпорт расширений в рабочую область текущего worktree; эталон и конфиг не меняет. |
| `edt remove [проект] [ветка]` | Как сейчас: рабочая область + git worktree, подтверждение по умолчанию. |
| `edt status [проект]` | Как сейчас. |
| `edt update [проекты]` | Для каждого проекта: проверка, что клон чистый и стоит на `ref_branch`, `fetch` + `merge --ff-only`, затем `warmup`. Занятые и конфликтные пропускаются с причиной. |
| `edt vr ...` | Как сейчас. |
| `edt doctor` | Проверки: PowerShell 7, git, EDT (какой будет использован), JVM для GUI (какая и почему), пути из конфига существуют, по каждому проекту: клон на `ref_branch`, рабочие расширения существуют, новые расширения не в списке, эталон есть. Каждая проблема — с командой исправления. Код возврата 1 при ошибках. |
| `edt config [show \| path \| set <ключ> <значение>]` | Показ, путь к файлу, точечная установка ключа (с валидацией формата). |
| `edt self-update`, `edt uninstall`, `edt help` | См. 4.2. |

Удаляются: `edt init`, `New-EdtProjectConfig`, `edt config init` (заменён
`edt setup`), все `wt-*` и `edt-wt-*`, ключи `-Validate`, `-Extensions`,
`-Force`, `-MaxHeap`, `-GuiMaxHeap` у `warmup`/`open`/`update`, чтение
`.edt-worktree.json`. Версия модуля — `3.0.0`.

Если `open`/`warmup` вызваны для папки клона, которая есть в `repos_root`, но
не зарегистрирована: в интерактивном сеансе сразу запускается диалог
`project add`, в неинтерактивном — ошибка с командой регистрации.

Автодополнение: подкоманды, подкоманды `project` и `config`, имена проектов,
имена расширений проекта после `+`/`-`.

## 7. Поведение

### 7.1. Обнаружение проектов в клоне

Поиск `.project` в клоне на глубину до 3 уровней (без `.git`). Конфигурация —
проект с nature `com._1c.g5.v8.dt.core.V8ConfigurationNature`, расширение — с
`com._1c.g5.v8.dt.core.V8ExtensionNature` (проверено на `ka-intertop-4edt`:
`src/cf`, `src/cfe*`). Если конфигураций несколько или ни одной — спросить
пользователя (в неинтерактивном режиме — ошибка с подсказкой `-CfProject`).

### 7.2. Эталон

- Каталог: `<workspaces_root>\<проект>\_reference`. Если есть старый
  `_reference_preprod`, а `_reference` нет и он не занят — переименовать.
- Источник — сам клон из `repos_root`. Перед сборкой: клон стоит на
  `ref_branch`, иначе отказ с объяснением. Отдельный worktree эталонной ветки не
  нужен.
- Состав: конфигурация + рабочие расширения, которых нет на диске, пропускаются
  с предупреждением; найденные, но не рабочие расширения перечисляются одной
  строкой с командой `edt project ext`.
- Всегда: импорт и затем `validate` по всем импортированным проектам (сейчас это
  поведение `-Validate`), из JVM-аргументов убирается `-DisableProjectChecks`.
- Всегда пересборка, безопасно: старый эталон отставляется (`.previous`),
  удаляется после успеха, возвращается при ошибке (как сейчас
  `Invoke-EdtWtSafeWarmup`).
- Если эталон занят процессом — отказ с указанием процесса; процессы не
  закрываются.
- Куча JVM — автоматически (как `Resolve-EdtWtJvmArgs`), если в конфиге не задан
  `edt.max_heap`.
- После сборки — перенос настроек IDE из `edt.prefs_source`, если задан.

### 7.3. Выбор JVM для GUI

Порядок:
1. `edt.vm_path` из конфига, если задан.
2. Если в `1cedt.ini` рядом с `1cedt.exe` уже есть `-vm` — `-vm` не передаётся
   (ini работает как задумано установщиком EDT).
3. `JAVA_HOME`, только если это JDK 17+ с JavaFX.
4. Известные каталоги JDK с JavaFX (Zulu FX, Axiom Full, Liberica Full в
   `Program Files`).
5. Ничего не найдено — запуск без `-vm` и предупреждение со ссылкой на
   `edt doctor`.

Все запуски GUI (включая перезапуск после `edt add`) идут через одну функцию.
`edt doctor` показывает выбранную JVM и причину выбора. Правило экранирования
путей с пробелами из AGENTS.md сохраняется.

### 7.4. Ветки и worktree

`edt open <проект> <ветка>`:
- `<ветка>` — полное имя (`feature/TASK-1`, `bugfix/x`). Короткое имя без `/`
  (`TASK-1`) дополняется `git.branch_prefix`.
- Каталог worktree: `<worktrees_root>\<проект>\<ветка с / → ->`.
- Если worktree ветки уже есть где угодно (`git worktree list`) — использовать
  его. Иначе: локальная ветка → `worktree add`; ветка на `<remote>` → создать
  локальную с отслеживанием; иначе — новая ветка от `<remote>/<ref_branch>`.
- Проект текущего каталога определяется по `git rev-parse --git-common-dir`:
  родитель `.git` — клон; его путь сравнивается с `repos_root\<проект>`.

## 8. Ограничения

- PowerShell 7+, Windows 10/11, git в PATH, 1C:EDT, JDK 17 с JavaFX.
- Правила AGENTS.md остаются в силе: UTF-8 с BOM для `.ps1`/`.psm1` с
  кириллицей, git только через `Invoke-EdtWtGit`, экранирование путей в
  `Start-Process`, формат `.location`, проверка
  `pwsh -NoProfile -File Invoke-EdtWtChecks.ps1` перед завершением.
- Работа без прав администратора.
- Каждое исправление и новая команда покрыты Pester-тестами; тесты не трогают
  реальный конфиг пользователя (`EDT_CONFIG_PATH` на временный файл).

## 9. Исправления из аудита

| # | Проблема | Решение в 3.0 |
|---|---|---|
| 1 | Эталонная ветка из конфига игнорируется | `ref_branch` у каждого проекта, одно место чтения; тест «установил → прочитал». |
| 2 | ID проекта в worktree = имя папки worktree | Нет конфига в репозитории; проект по `git-common-dir` (7.4); тест на worktree. |
| 3 | Сохранение стирает `projects` и др. | Сохранение всей схемы; тест round-trip. |
| 4 | `JAVA_HOME` перебивает рабочую JVM | Порядок выбора 7.3. |
| 5 | `edt add` перезапускает GUI без `-vm` и кучи | Один путь запуска GUI. |
| 6 | Зашит `D:\workspaces\full` | Только `edt.prefs_source`. |
| 7 | Зашиты `feature/`, `origin`, `src/<имя>`, `_reference_preprod` | `git.*`, относительные пути расширений, `_reference`. |
| 8 | Строковая сортировка версий EDT; путь к EDT замораживается | Сортировка по `[version]`; `cli_path: null` = автопоиск. |
| 9 | `uninstall` не чистит PATH | `edt uninstall` (4.2). |
| 10 | Поиск процессов по подстроке задевает `feature-T-10` при `feature-T-1` | Разбор `-data` из командной строки и сравнение нормализованных путей на равенство; без wildcard-сравнения. |
| 11 | Возможный deadlock чтения stdout/stderr `1cedtcli` | Асинхронное чтение обоих потоков. |
| 12 | В `.location` экранируются только пробелы | Экранирование всех символов, недопустимых в `java.net.URI` (`%` первым, пробел, `#`, `[`, `]`, `{`, `}`, `^`, `` ` ``, `"`, `<`, `>`, `|`), кириллица остаётся как есть. |
| 13 | README и COMMANDS.md про чужие dotfiles | Переписать под сценарий раздела 2: требования, установка, первые шаги, команды, конфиг, удаление, решение проблем. AGENTS.md обновить. |
| 14 | Установщик без проверок | 4.1. |
| 15 | ZIP помечается как скачанный | Основной путь — git clone; в README абзац про `Unblock-File` для ручной установки. |
| 16 | Нет `.gitattributes` | `*.cmd text eol=crlf`, `*.ps1 *.psm1 *.psd1 text eol=lf` (как сейчас в репозитории). |
| 17 | Бесполезный фолбэк поиска git в `self-update` | Убрать; git обязателен, `doctor` проверяет. |
| 18 | `Invoke-EdtWtChecks.ps1` падает без Pester 5 | Понятное сообщение с командой `Install-Module Pester -MinimumVersion 5 -Scope CurrentUser`. |

## 10. Решения, принятые мной (проверьте)

- Каталог установки по умолчанию `%LOCALAPPDATA%\EdtWorktree`.
- Мажорная версия 3.0 без старых имён команд; ваш конфиг мигрирует
  автоматически, legacy-файл остаётся на месте.
- Эталон собирается из самого клона, а не из отдельного worktree эталонной
  ветки; каталог эталона переименовывается в `_reference`.
- `edt add` остаётся как быстрый доимпорт в текущую рабочую область.
- Новые расширения в эталон сами не попадают — только подсказка.
- `edt update` и `warmup` не закрывают занятые IDE, а пропускают проект.
- Добавляется `edt doctor`.

## 11. Оставлено исполнителю

- Разбивка на файлы и имена внутренних функций (публичные имена PowerShell
  должны остаться понятными; `Invoke-EdtCommand` и алиас `edt` — точка входа).
